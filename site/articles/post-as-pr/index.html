Post a job as a pull request

OpenJob · November 20, 2026

Board

There is no posting form on OpenJob, no employer account, and no fee. A job is one Markdown file in one pull request on GitHub. About two minutes of typing, a check that runs itself, and the post is live — with a permalink every agent can read. This is the whole walkthrough.

Step 1 — Copy the template

Copy templates/job.md from github.com/softprobe/openjob. It is a YAML front matter block and a short body. The front matter you must fill in: kind (job), title, company (a slug), company_name, role_slug, location, remote (true, false, or hybrid — or the words remote, onsite, hybrid), languages, tags, apply, posted, and posted_by.

Step 2 — Set the apply method and your login

apply is required, and it has two shapes: an https:// link to an ATS, a careers page, or a LinkedIn job — or one mailto: address on the company website's own domain. To offer both, keep the https:// link in apply and put the mailto: in apply_email. A job has one hiring address; setting both fields to mailto: is rejected, as are shorteners, personal addresses, and addresses on any other domain. Set posted_by to your GitHub login — the login that will open the pull request. Set posted to today: a new post's posted date has to be within the last 45 days, and not more than two days in the future.

Optional fields, all backward compatible: employment_type (a schema.org value such as FULL_TIME), structured salary (min, optional max, ISO 4217 currency, unit of HOUR, DAY, WEEK, MONTH, or YEAR), structured locations, and a short compensation note. Leave salary out unless the number is real — do not invent one. The body, at least 40 characters, describes the work in plain words. Do not put an email address or a phone number in the body; the checker rejects both.

Step 3 — Save it in the right path

Save the file as jobs/YYYY/MM/<company>-<role-slug>.md, where YYYY/MM is the posted month. For example, a post dated November 2026 from Example Studio for an open-source maintainer goes at jobs/2026/11/example-studio-open-source-maintainer.md. The file must be UTF-8 Markdown, 10 KB or smaller, with at most 12 links.

Step 4 — Open a pull request with only that file

Open a pull request that adds only that file. A second new post is a separate pull request. If the company has no page yet, it can be added first in its own pull request — a company page lists its owners, is reviewed once by the maintainers, and does not auto-merge. After that, only those owners can add or edit that company's jobs; if there is no company page, only the login in posted_by can edit the job later.

Step 5 — Let the checker do the review

On the pull request, the validate workflow runs the unit tests and python -m validator check-pr. It checks the JSON Schema for the kind, the path and filename, the file size and format, the privacy rules, the link count (12), https on the structured links, no shorteners, and that the author owns every file. If anything fails, the bot comments with the code and the fix; push a fix and both checks run again. Posts are not reviewed by hand — the checker is the gate.

If the checks pass, the pull request squash-merges itself: the auto-merge workflow re-runs the check from the base branch and merges only when the validate check succeeded for the same head commit. The workflow then comments with the permalink and the share links for the post. A pull request that also edits workflows, docs, or the site does not auto-merge — the maintainers approve those.

After it is live

A job lasts 60 days from posted, or from renewed if you set it; you may set expires sooner, never later than the cap. To change the job, edit the same file in a new pull request and leave posted as it is. To renew it, set renewed to the day you open the pull request. To close it, delete the file in a pull request. Git history is the archive: expired files are removed from the live tree, and a post can be restored from the parent of the expiry commit.

That is the entire hiring flow: a file, a pull request, a check, a permalink. The job is then in the same public dataset every agent already reads — the board at openjob.softprobe.ai, the manifest at https://openjob.softprobe.ai/api/data/manifest.json, and the llms.txt your candidate's agent follows. The full rules, with an example file, are in CONTRIBUTING.md under "Post a job" at github.com/softprobe/openjob.

Try it yourself: paste "Read https://openjob.softprobe.ai/llms.txt and follow it. Find me a job." into the agent you already use — Muse, ChatGPT/Codex, Cursor, Hermes, or Instinct — and see what it finds. The board is at openjob.softprobe.ai; the source is github.com/softprobe/openjob.
